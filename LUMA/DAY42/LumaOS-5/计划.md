# 📅 LumaOS 5.0 → 9.0 总体开发 Schedule

> **说明**
>
> - 版本路线：**5.0 → 5.1 → 5.2 → 6.0 → 7.0 → 8.0 → 9.0**
> - 目标不是“模仿 Windows 的目录”，而是：**底层吸收 Unix 的优秀架构思想，用户体验与文件管理采用 LumaOS 自己定义的、偏 Windows 式的直观设计。**
> - LumaOS 的应用执行文件统一采用 **`.sw`（Luma Software）**。
> - 用户文件系统采用（⚠️ 早期草案，已被文末「LumaOS 9.0 目录架构规范」取代，仅保留作演进记录）：
>
> ```text
> System/
> User/
>   Administrator/
>   Public/
>   User_1/
> USB/
> IMG/
> ISO/
> ```
>
> - 外部存储/镜像的命名空间：
>
> ```text
> USB/DISK_1/
> USB/DISK_2/
> IMG/DISK_1/
> ISO/LumaOS/
> ```
>
> - 具体代码由 Claude 协作实现；每个 Day 的核心验收是：**代码能工作、你知道它解决了什么问题、你能测试并决定是否具备进入下一天的条件，说明核心的原理。**

## 🏛️ 核心架构变更（前30天必须定好）

| 新增目录 | 职责 |
| :--- | :--- |
| `kernel/drivers/block/` | IDE 硬盘驱动、分区解析（MBR） |
| `kernel/fs/vfs/` | 虚拟文件系统开关（挂载、打开、读、读目录） |
| `kernel/fs/fat/` | FAT12/16/32 具体实现 |
| `kernel/fs/lmfs/` | 你的专属 LMFS 实现 |
| `tools/` | `mkfs.lmfs`（用户态格式化工具，用 Python 写） |
| `iso/` | ISO 构建临时目录和脚本 |

**内核加载限制紧急调整（第 1 天必须做）**：

- `loader.asm`：`mov al, 128` → `mov al, 255`（读 255 扇区 ≈ 127.5 KB）
- `build.sh`：`MAX_LOAD=65536` → `MAX_LOAD=131072`
- 这样你加完所有 FS 代码（约 40~50 KB）后，总大小仍能控制在 100 KB 以内。

### 安全设计：复用已有的容错原则

这一步风险最高的操作是"把可引导分区从旧的切到新的"，直接对应 Day 12 讨论小结里的结论——**容错保底防的是写入过程中出问题，权限防的是谁能碰，升级安全靠的是验证完再切换**。安装程序据此设计为：

1. **先落地，再校验**：系统文件先整体写入目标分区的普通位置，写完后做一次完整性校验（例如比对文件大小/校验和），而不是边写边当作"已生效"。
2. **最后才切换引导标志**：只有校验全部通过后，才在最后一步（Day 90）把目标磁盘的分区标记为 Active、写入引导区——这是整个安装过程中唯一的高风险原子操作，且被安排在最后，尽量缩短"可能开不了机"的时间窗口。
3. **安装失败可重试**：只要引导标志还没切换，用户可以直接重跑安装程序，不会留下半成品；一旦切换失败（例如断电），保留原厂 ISO 仍可重新引导安装介质进行修复安装。

📝 关于内核引导 / 文件系统 / 升级的备注（Day 12 讨论小结）

现状（Day 1~12 做的事）：

Day 1~7：写 IDE 驱动，让内核脱离 BIOS 中断，自己读写磁盘扇区
Day 8~12：在扇区之上解析 FAT12 —— BPB 解析 → 挂载 → 簇链遍历 → fat12_readdir() 列根目录

为什么现在 ls 看不到 kernel.bin：

mbr.bin/loader.bin/kernel.bin 是 build.sh 用 dd 焊死在磁盘固定 LBA 上的裸二进制，跟文件系统无关
fat12_readdir() 挂载的是另一个独立的 FAT12 测试卷（tests/fat12-with-file.img，LBA 5000），两者互不重叠，ls 出来的自然是 BIGFILE.BIN/SMALL.BIN 而不是内核文件

Day 29 以后能不能让 kernel.bin 被 ls 看到：

可以，但不是"改现有机制"，而是额外在真正的文件系统（LMFS）里存一份 kernel.bin，专门给用户看/给 shell 用
固定 LBA 那份继续是引导专用，两者物理上独立，一份出问题不影响另一份

为什么 Windows 改 System32 会导致引导失败（对比理解）：

Windows 的引导链后半段（bootmgfw.efi → winload.efi → ntoskrnl.exe）是按文件路径动态查找内核，不是焊死扇区
这意味着文件系统里那份文件，从"摆设"变成了"引导链条上真正的一环"——删了/挪了，路径查找失败，引导直接断在那一步

权限（Administrator）能不能解决这个问题：

不能。权限管的是"谁能碰"（防手滑/防恶意），不是"碰坏了会不会崩"
即便是 Administrator 自己删了、或者磁盘坏道、或者升级中途断电写坏了文件，引导阶段权限系统根本没启动，一样会崩
结论：权限 ≠ 容错，是两层不同的防护，不能互相替代

那还能不能"系统内升级内核"：

能，标准做法是 "先落地验证，再原子切换"：
新内核先写到文件系统里一个新/临时位置，不动旧文件
校验新文件完整无误
确认没问题后，才把"生效指针"（或固定 LBA 那份）切换成新版本——这一步是唯一高风险操作，且基于"新版本已验证"的前提
旧版本保留一份做回退，不是直接删
Windows 用 WinSxS + 影子拷贝就是这个思路的实现
对应到 LumaOS：固定 LBA 保底那份，不需要是"项目第一天那份"，而应该是"当前已知最后一个能正常引导的版本"，跟着升级走，不是钉死不动

一句话记住：

容错保底防的是"写入过程中出问题"，权限防的是"谁能碰"，升级安全靠的是"验证完再切换 + 保留回退"——三件事互相独立，缺一不影响另外两个。对应路线图 Day 309~315（权限模型）和 Day 322（安装/升级机制）实现时要把这三层分开设计，不要指望其中一层替代另一层。

## 关于LMFS(LumaOS File System)

### milestone

#### 1. LMFS v1.0（当前阶段：Day 29～84 / LumaOS 5.0）

* **定位：** 极简可用（满足启动、加载 ELF、基本读写）。


* **结构：** 扁平化位图（Bitmap）+ 结构体 `lmfs_inode_t`（直接块/一级间接块/二级间接块）。


* **痛点：** 断电容易丢数据，大文件读取慢。



#### 2. LMFS v2.0（建议时期：LumaOS 7.0 多任务时代）

* **升级重点：** **引入区段（Extents）机制**。
* **改动点：**
* 在当前的 `lmfs_inode_t` 结构里，如果文件有 1000 个块，就需要写 1000 个块号。
* 改用 Extent 模式后，只需记录 `[起始块号: 100, 连续长度: 1000]`，大幅减少多级索引块的开销，提升磁盘 I/O 效率。
* **兼容性：** 在超级块的标志位（Flags）中增加一个 `LMFS_FEATURE_EXTENTS` 标志。旧版驱动读取到不认识的标志位会拒绝挂载，防止写坏磁盘。



#### 3. LMFS v3.0（建议时期：LumaOS 8.0/9.0 时代）

* **升级重点：** **日志系统（Journaling）**。
* **改动点：**
* 在磁盘元数据开辟一小块固定区域（Journal Area）。
* 任何写位图或修改 Inode 的操作，先“写日志”，再“刷盘”。
* 哪怕系统在运行中突然断电重启，开机时只需重放日志（Journal Replay），几毫秒内就能修复文件系统，彻底解决数据损坏问题。



#### 4. LMFS v4.0（未来 10.0+ 时代）

* **升级重点：** **动态目录索引（B+树 / H树）+ 扩展属性（xattr）**。
* **改动点：**
* 将简单的线性目录项匹配升级为 B+树，实现单目录下存几万个 `.sw` 应用也能瞬间检索。


* 增加扩展属性，用于存储文件的安全性标签、数字签名或应用图标元数据。

### 💡 如何在代码层确保 LMFS 未来可以平滑升级？

只要在 Day 29 定义超级块（Superblock）时做好以下两件事，你的 LMFS 就留足了未来 10 年的升级后路：

1. **版本号与特征标志位（Feature Flags）：**
在超级块中包含类似下面的结构：
```c
uint32_t magic;           // 0x4C4D4653 ("LMFS")
uint16_t version_major;   // 主版本（如 1）
uint16_t version_minor;   // 次版本（如 0）
uint32_t feature_compat;  // 兼容特性标志（旧内核读写无压力）
uint32_t feature_incompat;// 不兼容特性标志（遇到不支持的标志则拒绝挂载）
uint32_t feature_ro_compat;// 只读兼容标志（遇到不认识的标志，仅允许只读）

```


2. **预留空间（Padding / Reserved）：**
在超级块和 `lmfs_inode_t` 的结构体末尾，显式填入若干字节的预留数组，例如 `uint8_t reserved[32];`。未来升级增加新功能（比如追加日志起始 LBA、用户 ACL 权限指针）时，直接使用预留字节，而不需要破坏旧数据结构的对齐和大小。

用户账户与权限模块的用户态服务（Day 309~315）：账户模型、登录/Session、文件属主、权限校验逻辑。

## `IDE/System/Drivers/`
硬件驱动程序：块设备驱动（IDE/AHCI）、显卡/framebuffer 驱动、输入设备（键盘/鼠标）、网络设备驱动等。

## `IDE/System/Lib/`
系统共享库：libc 实现（`putchar`/`printf`/`malloc` 等，Day 71~74）、GUI SDK 运行时库、其他 `.sw` 程序链接时依赖的共享代码。

## `IDE/System/Sys/`
系统核心运行时组件（对应 Windows `System32` 定位）：内核直接依赖但不对用户暴露的底层可执行模块与运行时组件——例如 SW Loader 本体、Ring 3 切换相关的运行时桩代码、syscall 分发表相关的系统级二进制。普通用户和第三方应用不会直接访问这里的内容，只有内核/系统服务加载它们。

## `IDE/System/Config/`
系统级配置存储（Day 320 的 System Configuration Store）：全局设置、默认应用关联表（Day 319 的 File Association，如 `.bmp → ImageView.sw`）、应用注册表（Day 318 的 Application Registry）。

## `IDE/System/Temp/`
系统运行时临时文件：安装/升级过程中的中间产物、日志系统（LMFS v3.0）写入前的暂存区等，可随时清空。

---

## `IDE/User/User_x/`
每个普通用户一个独立目录（`User_1`、`User_2`……，命名与 Day 309 的 User Account Model 对应）。

- **`Desktop/`** — 桌面快捷方式与文件
- **`Documents/`** — 用户文档
- **`Downloads/`** — 下载文件
- **`Pictures/`** — 图片
- **`App/`** — 该用户私有安装的第三方 `.sw` 应用，仅当前用户可见/可用（Day 311 File Ownership 管控）

## `IDE/Administrator/`
管理员账户目录，结构与普通用户类似但额外具备系统管理权限（Day 313）。

- **`Index/`** — 系统级索引/审计记录，供管理员查看系统状态、文件索引等管理专用数据（区别于普通用户看不到的管理视图）
- **`Desktop/` / `Documents/`** — 同普通用户
- **`App/`** — 管理员私有安装的应用

## `IDE/Public/App/`
**全局第三方应用安装位置**：任何用户安装后勾选"所有人可用"的第三方 `.sw` 软件放这里，所有账户都能看到和运行（对应 Day 317 Application Installer 的"全局安装"选项）。与 `SysApp/` 的区别：`Public/App/` 里的是用户自己装的第三方软件，`SysApp/` 是系统自带、不可卸载的官方应用。

## `USB/DISK_1/`、`USB/DISK_2/`
外接 USB 存储设备的挂载点，按插入顺序编号。

## `IMG/DISK_1/`
磁盘镜像文件的挂载/访问入口（如 `.img` 格式的虚拟磁盘）。

## `ISO/LumaOS/`
ISO 镜像的存放与访问目录，对应 Day 57~63 的 ISO9660/El Torito 引导支持。
