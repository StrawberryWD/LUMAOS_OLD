LumaOS 5.0 - LMFS (Luma File System) 超级块设计文档

DAY29 (第二月 · 第5周 · Day 29):
  "设计 LMFS 超级块布局（位于 LBA 1）：魔数 0x4C4D4653、版本号、
   inode 数量、数据块数量、inode 位图起始 LBA、数据块位图起始 LBA。"

  这是 LMFS（LumaOS 自己的专属文件系统）的第一份设计文档，产出是
  "文档"而不是代码——Day 1~28 的 FAT12/16/32 是在"解析别人已经定好的
  格式"，超级块布局是别人焊死的，我们没有设计空间；从今天起 LMFS
  是我们自己从零定义的格式，所以第一步不是写 .c/.h，而是先把"磁盘上
  第 X 个字节是什么意思"想清楚、写下来，Day 31 起才照着这份文档去写
  真正的 lmfs.h/lmfs.c。这也是为什么第 5 周的任务分成两天纯设计
  （Day 29 超级块、Day 30 inode）——磁盘格式一旦上线不好改，多花一天
  想清楚，比写完代码才发现漏了字段划算。

================================================================================
一、"LBA 1"指的是谁的 LBA 1？—— 卷内相对地址，不是磁盘绝对地址
================================================================================

计划里写"位于 LBA 1"，容易被误读成"整个磁盘镜像的绝对第 1 扇区"。
但看现有的 build.sh 磁盘布局：

    绝对 LBA 0        mbr.bin    （512 字节引导记录）
    绝对 LBA 1 ~ 5    loader.bin （第二阶段引导器，5 个扇区）
    绝对 LBA 6 ~ 261  kernel.bin （内核本体）
    绝对 LBA 2500     tests/fat12-bpb.bin   （FAT12 BPB 测试卷）
    绝对 LBA 5000     tests/fat12-with-file.img （FAT12 测试卷）
    绝对 LBA 10000    tests/fat16-with-file.img （FAT16 测试卷）
    绝对 LBA 30000    tests/fat32-with-file.img （FAT32 测试卷）

如果把 LMFS 超级块焊死在"磁盘绝对 LBA 1"，会直接砸在 loader.bin
头上——这是致命冲突，不能这么做。

本项目里 FAT12/16/32 测试卷早就示范过正确的做法：每个卷从"自己的
LBA 0"开始独立编号（fat12-with-file.img 内部的簇/扇区号都是相对
自己卷首算的），卷被 dd 到磁盘哪个绝对位置（5000、10000、30000...）
是"挂载/嵌入时"才决定的外部信息，跟卷内部的格式定义无关。

所以本文档对"LBA 1"的解读是：**LMFS 卷自己的 LBA 0 是这个卷的引导
扇区/保留扇区，LBA 1（即卷首 + 1 个扇区偏移，512 字节 × 1 = 偏移
0x200 字节处）放超级块**——这是卷内相对地址，完全独立于这个卷将来
被烧录到磁盘哪个绝对 LBA。等 Day 85~91 做"安装到硬盘"、或者更早
测试阶段需要把 LMFS 卷嵌入到 build.sh 生成的镜像里时，会像
fat32-with-file.img 那样另选一个不冲突的绝对 LBA（沿用本项目一贯
"挑一个远离已用区域的安全位置"的方法），到时候会在 build.sh 里
写清楚并更新本文档，但那是实现阶段（Day 31 之后）的事，不影响今天
的格式设计。

    LMFS 卷内部布局（本阶段设计范围）：

        卷内 LBA 0   : 保留扇区 / 卷引导扇区（本阶段占位，暂不使用，
                        为将来"卷本身也能被引导"之类的扩展留空间）
        卷内 LBA 1   : 超级块（lmfs_superblock_t，本文档的主题）
        卷内 LBA 2 ~ : inode 位图 / 数据块位图 / inode 表 / 数据区
                        （起始位置由超级块里的字段给出，具体划分
                        等 Day 30 定完 inode 结构、块大小之后再确定）

================================================================================
二、超级块结构 lmfs_superblock_t（设计稿，非最终代码）
================================================================================

    typedef struct {
        /* --- Day 29 要求的核心字段 --- */
        uint32_t magic;             /* 0x4C4D4653 = ASCII "LMFS"        */
        uint16_t version_major;     /* 主版本号，当前 = 1               */
        uint16_t version_minor;     /* 次版本号，当前 = 0               */
        uint32_t inode_count;       /* 本卷 inode 总数                  */
        uint32_t data_block_count;  /* 本卷数据块总数                   */
        uint32_t inode_bitmap_lba;  /* inode 位图起始 LBA（卷内相对）   */
        uint32_t data_bitmap_lba;   /* 数据块位图起始 LBA（卷内相对）   */

        /* --- 为未来升级预留的字段（详见第三节） --- */
        uint32_t feature_compat;    /* 兼容特性标志：旧驱动可忽略        */
        uint32_t feature_incompat;  /* 不兼容特性标志：不认识就拒绝挂载  */
        uint32_t feature_ro_compat; /* 只读兼容标志：不认识就只挂只读    */

        uint8_t  reserved[476];     /* 预留字节，补齐到 512 字节整扇区  */
    } lmfs_superblock_t;            /* sizeof == 512（1 个磁盘扇区）    */

字节偏移表（从超级块自己的起始处，即卷内 LBA 1 的第 0 字节算起）：

    偏移量        大小   字段
    ------------  -----  --------------------
    0x000 (0)     4      magic
    0x004 (4)     2      version_major
    0x006 (6)     2      version_minor
    0x008 (8)     4      inode_count
    0x00C (12)    4      data_block_count
    0x010 (16)    4      inode_bitmap_lba
    0x014 (20)    4      data_bitmap_lba
    0x018 (24)    4      feature_compat
    0x01C (28)    4      feature_incompat
    0x020 (32)    4      feature_ro_compat
    0x024 (36)    476    reserved
    ------------  -----  --------------------
    总计          512    == 1 个 512 字节扇区（1 LBA）

    为什么整体大小刚好凑成 512 字节：超级块本来就整个占用卷内 LBA 1
    这一个扇区，读写它天然就是"读 1 个扇区、写 1 个扇区"，不需要
    再处理"结构体只用了扇区的一部分，剩下半截是垃圾数据"这种情况；
    reserved 数组既是对齐手段，也是第三节说的"给未来功能留空间"。

================================================================================
三、字段详解
================================================================================

magic (0x4C4D4653)
    'L'=0x4C 'M'=0x4D 'F'=0x46 'S'=0x53，ASCII 拼出 "LMFS"。跟
    fat_common.h 里 fat_detect_type() 认 BS_FilSysType 字符串是同一
    个思路：挂载时先读这 4 个字节，对不上就说明这不是 LMFS 卷（或者
    卷头损坏），直接拒绝挂载，不往下走，避免把无效数据当文件系统用。

version_major / version_minor
    拆成两个 uint16_t 而不是一个 uint32_t，是因为"主版本变了"和
    "次版本变了"驱动要做的事完全不同：次版本升级（比如 1.0 -> 1.1）
    通常只是加了新的可选特性，老驱动大多还能正常读写；主版本升级
    （1.x -> 2.x，比如本文档"关于 LMFS"milestone 一节说的 v2.0 引入
    Extents）往往意味着磁盘布局的根本变化，老驱动继续用旧逻辑读
    很可能直接读错。拆开存，挂载代码可以分别判断，而不是把两种性质
    不同的"变化"糊成一个数字比大小。

inode_count / data_block_count
    这个卷总共能容纳多少个 inode（等于能容纳多少个文件/目录）、
    总共有多少个数据块可用。这两个数字是 mkfs（格式化）时根据卷的
    总容量、按什么比例切分 inode 区和数据区决定的——具体切分比例
    不是 Day 29 的题目，等 Day 30 定完 inode 结构大小、以及后面
    真正写 mkfs 工具时才会给出公式；今天先把"超级块要能存下这两个
    数字"这件事定下来。

inode_bitmap_lba / data_bitmap_lba
    inode 位图、数据块位图各自的起始 LBA（卷内相对地址，含义同第一
    节）。位图是"一个 bit 对应一个 inode / 一个数据块，标记这个
    inode / 块有没有被占用"的经典分配结构——有了这两个字段，挂载代码
    不需要"猜"位图放在哪，直接从超级块读出来定位，这也是为什么这两
    个字段必须放在超级块里而不是写死在代码常量里：万一以后 Day 30
    定下 inode 结构大小后，两个位图的位置要跟着重新计算，只要 mkfs
    写的时候把算好的值填进超级块，挂载代码完全不用改。

feature_compat / feature_incompat / feature_ro_compat
    这三个字段不是 Day 29 任务清单里点名要的字段，是"关于 LMFS"
    milestone 一节里明确建议现在就加上的："只要在 Day 29 定义超级块
    时做好...你的 LMFS 就留足了未来 10 年的升级后路"。三者含义各不
    相同：
      - feature_compat：可选特性标志。驱动看不懂某一位也没关系，
        照常读写，只是用不上那个新特性。
      - feature_incompat：不兼容特性标志。驱动看到自己不认识的位，
        必须拒绝挂载——因为这意味着磁盘上的数据布局用了这个驱动
        看不懂的规则（milestone 里举的例子：v2.0 的 LMFS_FEATURE_EXTENTS，
        旧驱动如果硬挂载，会把 extent 编码的块列表当成传统的逐块
        列表来解析，读出一堆垃圾地址）。
      - feature_ro_compat：只读兼容标志。驱动不认识就只允许只读
        挂载，禁止写入——防止旧驱动用旧逻辑写坏新特性用到的数据
        结构，但至少还能把数据读出来、不影响"能不能看到文件"。
    这三个字段今天全部设为 0（本版本 v1.0 没有用到任何可选/不兼容
    特性），但位置先占好，v2.0 引入 Extents 时才有地方放标志位，
    不需要改超级块结构体本身（不改结构体大小/布局，就不会让"新
    mkfs 格式化的卷"和"老驱动"在结构对齐上直接对不上）。

reserved[476]
    补齐到 512 字节的预留空间，全部初始化为 0。跟 fat_common.h 系列
    文件一路示范的风格一致：预留字节不是"浪费"，是"以后加字段（比如
    milestone 提到的日志区起始 LBA、用户 ACL 权限指针）时，直接切一段
    reserved 用，不用挪动前面任何一个已有字段的偏移量"——旧版本格式化
    的卷、新版本的驱动，只要新字段是从 reserved 里切出来的，双方对
    "前面那些字段在哪"的理解永远一致，不会出现"新驱动以为 inode_count
    在偏移 8，实际上因为中间插了新字段变成偏移 12"这种错位。

四、Day 29 明确不做的事（留给之后）
================================================================================

  - 不定义块大小（block size）——Day 30 的任务（milestone 一节写明
    v1.0 用 1024 字节/块，但那是 Day 30 定 inode 结构时一起定的，
    今天的超级块字段里也确实没有 block_size，先不提前加，保持跟
    计划里 Day 29 的字段清单一致）。
  - 不定义 inode 表起始 LBA / 数据区起始 LBA——这两个位置依赖
    inode_count、inode 结构大小（Day 30 才定）才能算出来，今天超级块
    里也确实只要求了两个位图的位置，没要求这两个。
  - 不写 lmfs.h / lmfs.c、不写 mkfs 工具——今天的产出就是这份文档，
    代码从 Day 31 起才会陆续出现。
  - 不涉及日志（Journaling，milestone 里的 v3.0）、B+树目录、xattr——
    都是 v2.0/v3.0/v4.0 才做的事，v1.0 阶段（Day 29~84）故意不做，
    避免一开始就把简单能跑的东西做复杂。

五、验收
================================================================================

本文档本身就是 Day 29 的验收物——存在 doc/lmfs.txt，写清楚了：
魔数 0x4C4D4653、版本号（拆成 major/minor）、inode 数量、数据块
数量、inode 位图起始 LBA、数据块位图起始 LBA 六个必需字段，外加
预留的 feature flags 和 reserved 空间；并且说明了"LBA 1"是卷内
相对地址、不会跟现有磁盘布局（loader.bin 占据绝对 LBA 1~5）冲突。

Day 29 不产出可执行代码、不修改磁盘镜像、不涉及内核/引导逻辑，
因此没有可以在 QEMU 里跑起来验证的东西——今天的"跑通"就是这份
文档能自洽地回答"超级块长什么样、每个字段干什么用"。Day 30 设计
完 inode 结构后，Day 31 起才会有真正需要在 QEMU 里跑的代码。


================================================================================
六、块大小定义：1024 字节
================================================================================

DAY30 (第二月 · 第5周 · Day 30):
  "设计 inode 结构（lmfs_inode_t）：包含文件大小、创建时间、直接块
   指针 8 个 + 间接块指针 1 个 + 二级间接块 1 个（支持大文件）。
   验收：定义块大小 1024 字节（适合软盘/小硬盘）。"

块大小（block size）是"数据区最小分配单位"，inode 里的每一个块指针
指的都是"第几个这么大的块"，所以设计 inode 之前必须先把这个数定下来
——这也是为什么 Day 30 的验收标准反而是"定义块大小"，而不是"inode
结构定义完成"：块大小是 inode 设计能成立的前提，不是附带产出。

选 1024 字节（而不是跟磁盘扇区一样的 512，或者现代硬盘常见的 4096）：

  - 512 字节等于 1 个扇区，块粒度太细：一个稍大点的文件（比如几十
    KB）光是直接块 8 个（8×512=4KB）就远远不够，马上就要走间接块，
    小文件也占不到什么便宜。
  - 4096 字节对软盘（1.44MB）这种小容量介质浪费太明显：哪怕只存一个
    10 字节的文件，也要占掉一整个 4KB 块，milestone 里明确写了 v1.0
    "适合软盘/小硬盘"，4096 不合适。
  - 1024 字节（= 2 个扇区）是折中：小文件浪费可控，8 个直接块就能
    覆盖 8KB 以内的绝大多数配置文件/小文本，同时配合间接块/二级间接
    块也能支持到几十 MB 的大文件（具体算式见下一节）。

    #define LMFS_BLOCK_SIZE 1024   /* 字节 */

    块号与 LBA 的换算关系：LMFS 里"块号 N"对应卷内 LBA = N * 2
    （因为 1 个块 = 1024 字节 = 2 个 512 字节扇区）。挂载/读写代码
    统一通过这一个换算点转换，不会出现有的地方按扇区数、有的地方
    按块数直接混用的问题。

================================================================================
七、inode 结构 lmfs_inode_t（设计稿，非最终代码）
================================================================================

    typedef struct {
        uint32_t file_size;      /* 文件实际大小，单位：字节           */
        uint32_t created_time;   /* 创建时间戳（见下方字段详解）        */
        uint8_t  type;           /* 0=空闲 1=普通文件 2=目录（见详解）  */
        uint8_t  reserved0[3];   /* 补齐到 4 字节对齐，暂不使用         */
        uint32_t direct[8];      /* 8 个直接块指针                     */
        uint32_t indirect1;      /* 一级间接块指针                     */
        uint32_t indirect2;      /* 二级间接块指针                     */
        uint8_t  reserved1[12];  /* 预留，补齐到 64 字节                */
    } lmfs_inode_t;               /* sizeof == 64 字节                 */

字节偏移表：

    偏移量        大小   字段
    ------------  -----  --------------------
    0x00 (0)      4      file_size
    0x04 (4)      4      created_time
    0x08 (8)      1      type
    0x09 (9)      3      reserved0（对齐用）
    0x0C (12)     32     direct[0..7]（每个 4 字节 × 8）
    0x2C (44)     4      indirect1
    0x30 (48)     4      indirect2
    0x34 (52)     12     reserved1
    ------------  -----  --------------------
    总计          64     字节

    为什么定成 64 字节而不是"字段用多少算多少"（实际字段只用了
    52 字节）：64 能被块大小 1024 整除（1024 / 64 = 16），意味着
    inode 表里每个块恰好装 16 个完整的 inode，不会出现"第 16.5 个
    inode 跨在两个块中间"这种要拆两次读写才能拼出一个完整 inode 的
    麻烦情况。这跟超级块补齐到 512 字节（正好 1 个扇区）是同一个
    思路：让"结构大小"和"底层存储单位"对齐，访问逻辑最简单。

================================================================================
八、字段详解
================================================================================

file_size
    文件当前的真实字节数（不是占用了多少块——最后一个块通常用不满，
    file_size 记的是精确字节数，读文件时用它决定最后一块要读多少
    字节，而不是整块都当作有效数据）。

created_time
    预留的创建时间戳字段，类型先定为 uint32_t（足够存经典 32 位
    Unix 时间戳，到 2106 年才溢出，v1.0 阶段够用）。本项目目前
    没有 RTC（实时时钟）驱动——fat_common.h 里 FAT 的 DIR_*Time
    字段就是因为同样的原因，一直只能写 0（该文件注释原话："this
    project having no real-time clock driver yet, 0 is a legal, if
    uninformative, timestamp"）。LMFS 沿用同一个约定：字段先占好
    位置，Day 31 起 mkfs/lmfs_create() 实际写 inode 时先统一填 0，
    等以后哪天加了 RTC 驱动，只需要改"填什么值"这一行，不需要改
    inode 结构、不需要处理"老文件没有时间戳"的兼容问题（反正从
    v1.0 第一个 inode 开始就已经有这个字段了，只是值不准而已）。

type（补充字段，不在 Day 30 原始字段清单里，见下方说明）
    Day 30 任务描述本身只列了"文件大小、创建时间、直接块指针、间接
    块指针"，没提字段区分"这是文件还是目录"。但 Day 31 的验收标准
    是"...创建根目录 inode"——根目录本身就必须是一个 inode，而且
    必须能被认出"这个 inode 代表的是目录，不是普通文件"，否则
    Day 34 lmfs_readdir()、Day 42 多级目录解析都无法判断"该往哪个
    inode 里找子目录项"。所以这里把 type 字段提前加进 Day 30 的
    inode 设计里，取值约定为：0 = 该 inode 槽位空闲未使用（配合
    inode 位图，位图说"没占用"时这里也应该是 0，两者一致），
    1 = 普通文件，2 = 目录。如果你希望这个区分留到更后面的 Day
    （比如单独用一天设计目录项格式时再加），告诉我，我把这个
    字段挪到 reserved 里去，现在先按"现在加，免得 Day 31 卡住"
    的思路处理。

direct[8]（8 个直接块指针）
    每个是一个块号（配合第六节的换算关系，块号 × 2 = 卷内 LBA），
    直接指向存数据的块，不需要多绕一层。8 个直接块 × 1024 字节 =
    8192 字节——这是"零额外开销"就能表示的文件大小上限，绝大多数
    小文件（Shell 脚本、配置、短文本）一个间接块都用不上，读写时
    inode 里直接就是块号，少一次额外的磁盘读。

indirect1（一级间接块指针）
    指向"一个块"，这个块里存的不是数据，而是 1024 / 4 = 256 个
    uint32_t，每个是一个数据块的块号——相当于给 direct 数组续了
    256 格。所以通过一级间接块能多表示 256 × 1024 = 262144 字节
    （256 KB）。读取时要先读这一个"索引块"，再按里面某一项去读真正
    的数据块，比直接块多一次磁盘 I/O，但只有文件大小超过 8KB 才会
    用到。

indirect2（二级间接块指针）
    指向"一个索引块"，这个块里的 256 个 uint32_t 每一个又指向另一个
    "一级索引块"（跟 indirect1 指向的那种块结构完全一样），那些
    一级索引块里的 256 个指针才是真正的数据块。所以二级间接块能
    表示 256 × 256 × 1024 = 67108864 字节（64 MB）。读取时要先读
    二级索引块，再读它指向的某个一级索引块，再读数据块，一共三次
    额外 I/O 才能定位到数据——只有巨大文件才会用到这一层，符合
    milestone 里"支持大文件"的要求，但访问代价也最高，这是所有
    经典 Unix 风格 inode（ext2 等）都用这套"直接+间接+二级间接"
    分级结构而不是"全用间接块"的原因：小文件走最快的路径（直接
    块，0 次额外 I/O），只有真正的大文件才承担多级索引的开销。

    单个 inode 能表示的最大文件大小 = 直接块 + 一级间接 + 二级间接：

        8192 + 262144 + 67108864 = 67,379,200 字节 ≈ 64.26 MB

    对"软盘/小硬盘"场景（milestone 原话）完全够用，且实现复杂度
    停在"三级索引"，不需要 ext2 那样的三级间接块。

reserved0[3] / reserved1[12]
    跟超级块的 reserved 字段同一个道理：reserved0 纯粹是把 type
    这 1 个字节补齐到 4 字节边界（让紧跟着的 direct[8] 数组从 4
    字节对齐的偏移开始，x86 按 4 字节对齐访问 uint32_t 效率更好、
    也更不容易在未来移植到对齐要求更严格的架构时出问题）；
    reserved1 是给以后加字段用的余量（比如 milestone v4.0 提到的
    xattr 指针、或者以后想加的"修改时间/访问时间"跟 created_time
    放在一起），加进去不需要挪动前面任何已有字段的偏移，逻辑跟
    Day 29 超级块 reserved 字段的理由完全一样。

九、结合超级块：现在可以说清楚的卷整体布局
================================================================================

有了块大小（1024 字节）和 inode 大小（64 字节）之后，LMFS 卷内部
从头到尾的区域顺序可以完整地写出来了（具体每个区域各占多少块，
取决于格式化时选定的 inode_count / data_block_count，由 Day 31
的 tools/mkfs.lmfs 按卷总容量算出来，今天只定顺序，不算具体数字）：

    卷内 LBA 0     ：保留扇区（本阶段占位不用，见第一节）
    卷内 LBA 1     ：超级块（lmfs_superblock_t，Day 29）
    往后           ：inode 位图（大小 = ceil(inode_count / 8) 字节，
                     起始 LBA 记在超级块 inode_bitmap_lba 里）
    再往后         ：数据块位图（大小 = ceil(data_block_count / 8)
                     字节，起始 LBA 记在超级块 data_bitmap_lba 里）
    再往后         ：inode 表（inode_count 个 lmfs_inode_t，每块
                     16 个，共 ceil(inode_count / 16) 个块；这个区域
                     的起始位置本文档不新增字段去存——通过
                     "data_bitmap_lba + 数据块位图占用的块数" 直接
                     算出来，不需要在超级块里再存一个 inode_table_lba，
                     减少一个"两处数据要保持一致"的冗余字段）
    再往后（到卷尾）：数据区（存放所有文件/目录的实际内容，就是
                     direct/indirect1/indirect2 里的块号所指向的
                     地方）

    inode 编号约定：inode 0 = 根目录（对应 Day 31"创建根目录 inode"、
    Day 33 验收"能读取 inode 0"——这两条合在一起说明根目录就是 0 号
    inode，这里把这个约定明确写下来，Day 31 mkfs 和 Day 32/33 的
    lmfs_mount()/lmfs_read_inode() 都按这个约定实现，不需要再另外
    找地方存"根目录 inode 号是几"）。

文件名长度：不沿用 FAT 的 8.3
--------------------------------------------------------------------------
计划.md 文末「LumaOS 9.0 目录架构规范（权威/最终版）」是全文档目录
结构的唯一权威定义，里面出现的目录/文件名——"Administrator"（13
字符）、"TaskManager.sw"/"FileManager.sw"（14 字符）、"SystemInfo.sw"
（13 字符）等——已经超出 FAT 8.3 格式（8+3=11 字符）能装下的范围。
LMFS 是 LumaOS 自己的原生文件系统，没有理由继承 FAT 的历史限制，
所以目录项的文件名字段直接设计成"够长的定长字符串"，而不是像 FAT
那样短名+扩展名分开存、还要处理大小写折叠这些历史包袱。

目录项结构 lmfs_dirent_t（64 字节，跟 inode 同样大小，同样的理由：
能整除块大小，1024/64=16，一个块正好装 16 个目录项）：

    typedef struct {
        uint32_t inode_num;      /* 这个目录项指向的 inode 号        */
        uint8_t  used;           /* 0=空闲(未使用/已删除) 1=已使用   */
        uint8_t  name_len;       /* 名字实际字符数，不含结尾 NUL     */
        uint8_t  reserved[2];    /* 对齐/预留                        */
        char     name[56];       /* NUL 结尾，最长 55 个字符          */
    } lmfs_dirent_t;              /* sizeof == 64                    */

字节偏移表：

    偏移量        大小   字段
    ------------  -----  --------------------
    0x00 (0)      4      inode_num
    0x04 (4)      1      used
    0x05 (5)      1      name_len
    0x06 (6)      2      reserved
    0x08 (8)      56     name
    ------------  -----  --------------------
    总计          64     字节

用独立的 used 字段，而不是像 FAT 那样把"名字第一个字节"兼职当空闲
标记（0x00=结束、0xE5=已删除）：因为 LMFS 的文件名是真正的变长文本，
理论上第一个字符是任何 ASCII 字符都合法（虽然目前 mkfs.lmfs 从不
生成以特殊字符开头的名字），不能像 FAT 那样牺牲名字的某个字节位置
去表达元信息。used=0 就是空闲/已删除，used=1 就是已使用，逻辑上更
干净，代价只是每条目录项多花 1 个字节——对已经把 inode/dirent 都
定成 64 字节、本来就有富余对齐空间的 LMFS 来说完全不算什么。

数据块号 0 是保留哨兵值
--------------------------------------------------------------------------
inode 的 direct[]/indirect1/indirect2 都需要一个"这个指针槽位没有
指向任何块"的表示方式。参照"inode 0 永远有意义、代表根目录"这个
已有约定的反面：**数据块号 0 永远没有意义，代表指针为空**，真正能
分配给文件/目录内容的数据块号从 1 开始。mkfs.lmfs 格式化时会在数据
块位图里把第 0 位直接标记为已占用（永久保留，不属于任何 inode）；
Day 36/37 设计位图分配算法时，也要遵守"永远跳过块号 0"这条规则。

这个决定现在才提出，是因为直到 Day 34 要往根目录里真正写一个数据块
之前，"块号 0 到底能不能被分配"这个问题都不会被触发——但既然现在
触发了，就要一次性定下来，不能拖到以后每次遇到"这个指针是 0，到底
是'合法的块号 0'还是'没有块'"时才现场猜。

根目录内容：mkfs.lmfs 现在会往里面写什么
--------------------------------------------------------------------------
Day 31 当初生成的根目录是完全空的（file_size=0，不占用任何数据块）
——这在"能列出根目录"这个验收标准下无法验证 lmfs_readdir() 真的在
正确解析目录项，只能验证"空目录返回 0 条"这一种情况。所以 mkfs.lmfs
现在给根目录分配了块号 1（LMFS_ROOT_DIR_BLOCK_NUM）作为它的第一个
数据块，写入两条固定的目录项：

    "."   -> inode 0（根目录指向自己）
    ".."  -> inode 0（根目录的父目录约定为自己，跟大多数 Unix 系统
                       "根目录是自己的父目录"的约定一致）

根目录 inode 相应更新：file_size = 1024（1 个块），direct[0] = 1，
direct[1..7]/indirect1/indirect2 全部是 BLOCK_NONE(0)。目录的
file_size 在这里的含义是"已经分配了多少字节的块装目录项数据"（即
已分配块数 × 块大小），不是"实际写了多少字节的有效目录项"——块内
没用到的槽位（这里是 16 个槽位里的 14 个）靠 used=0 标记为空闲，
不需要 file_size 精确到字节；这跟"目录的 file_size 按块对齐"是绝大
多数经典 Unix 文件系统的通行做法一致，也让 lmfs_readdir() 的实现
可以简单地"扫描 inode 声明的每一个已分配块，逐槽位看 used"，不需要
用 file_size 做字节级别的边界截断。
